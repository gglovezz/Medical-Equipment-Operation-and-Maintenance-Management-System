# 医疗设备运维管理系统 需求分析文档

> 版本：v1.0
> 最后更新：2026-11-10
> 项目类型：Android App + Spring Boot 后端
> 开发周期：6-8 周

---

## 一、项目概述

### 1.1 项目背景

医院设备科需要管理全院医疗设备的台账、巡检、报修与检定工作。传统方式依赖纸质单据和 Excel，存在以下痛点：

- 护士发现设备故障后报修流程慢，找不到对接人；
- 设备巡检靠人工记忆，容易漏检；
- 计量检定到期设备不能及时发现，存在合规风险；
- 设备台账分散，统计报修数据全靠手动整理。

本项目做一个 **Android App + Spring Boot 后端** 的轻量化解决方案，覆盖"设备台账 → 扫码报修 → 工单流转 → 巡检打卡 → 统计报表"全流程。

### 1.2 项目目标

- 独立完成前后端开发，作为简历项目；
- 核心业务闭环：用户登录 → 扫码查看设备 → 提交报修 → 工单流转 → 完成评价；
- 后端具备完整的鉴权、权限、缓存、定时任务能力；
- Android 端具备完整的网络请求、本地缓存、图片上传、扫码能力。

### 1.3 用户角色

| 角色 | 说明 | 权限范围 |
|---|---|---|
| **管理员（admin）** | 设备科负责人 | 全部设备、全部工单、用户管理、统计报表、导出 |
| **设备科人员（engineer）** | 维修工程师 | 查看受理中的工单、接单、派单、完工、巡检任务处理 |
| **临床护士（nurse）** | 设备使用人 | 扫码查看设备、提交报修、查看自己提交的工单、评价完工工单 |

> 说明：第一版不做"护士"和"普通员工"的细分，统一用 `nurse` 角色即可。

## 二、功能需求

### 2.1 功能清单总览

| 模块 | 功能点 | 角色 | 优先级 |
|---|---|---|---|
| 用户模块 | 登录、Token 刷新、获取当前用户信息、修改密码 | 全部 | P0 |

| 导出 | 导出月度报修 Excel | admin | P2 |

### 2.2 用户模块

#### 2.2.1 登录

- **入口**：App 启动页 → 登录页
- **输入**：用户名、密码
- **后端接口**：`POST /api/auth/login`
- **请求体**：
  ```json
  { "username": "zhangsan", "password": "123456" }
  ```
- **响应体**：
  ```json
  {
    "code": 200,
    "message": "success",
    "data": {
      "token": "eyJhbGciOi...",
      "expiresIn": 7200,
      "userInfo": {
        "userId": 1,
        "username": "zhangsan",
        "realName": "张三",
        "role": "nurse",
        "dept": "内科"
      }
    }
  }
  ```
- **异常**：
  - 用户名或密码错误：`code=1001, message="用户名或密码错误"`
  - 账号被禁用：`code=1002, message="账号已禁用，请联系管理员"`
- **App 行为**：
  - 登录成功后，token 存入 DataStore；
  - 根据 `role` 跳转到不同首页：
    - `admin` → 管理首页（设备列表 + 统计）
    - `engineer` → 工单首页（待受理工单列表）
    - `nurse` → 报修首页（扫码按钮 + 我的工单）

#### 2.2.2 Token 自动刷新

- App 的 OkHttp 拦截器统一处理：
  - 请求头加 `Authorization: Bearer {token}`；
  - 收到响应 `code=401` 时，用 refreshToken（第一版简化：直接跳回登录页）重新登录；
- 第一版简化：不做 refreshToken，token 过期直接跳登录页。

#### 2.2.3 修改密码

- **入口**："我的"页面 → 修改密码
- **输入**：原密码、新密码、确认新密码
- **接口**：`PUT /api/user/password`
- **校验**：原密码正确、新密码长度 6-20 位、两次输入一致

### 2.3 设备台账模块

#### 2.3.1 设备列表

- **接口**：`GET /api/device/page?pageNum=1&pageSize=10&keyword=呼吸机&dept=内科&status=1`
- **响应**：分页结构
  ```json
  {
    "code": 200,
    "data": {
      "total": 56,
      "list": [
        {
          "id": 101,
          "deviceName": "无创呼吸机",
          "model": "SV-300",
          "snCode": "WH20240001",
          "department": "内科",
          "status": 1,
          "nextInspectDate": "2026-12-01"
        }
      ]
    }
  }
  ```
- **设备状态枚举**：
  | 值 | 含义 |
  |---|---|
  | 1 | 正常使用 |
  | 2 | 维修中 |
  | 3 | 停用/报废 |
  | 4 | 检定中 |

#### 2.3.2 设备详情

- **接口**：`GET /api/device/{id}`
- **返回字段**：设备全部信息，包括：
  - 基础信息：名称、型号、SN、所属科室、位置、采购日期、供应商；
  - 状态信息：当前状态、上次巡检日期、下次巡检日期、计量检定到期日期；
  - 关联信息：该设备最近 5 条报修工单。

#### 2.3.3 新增/编辑设备

- **角色**：admin
- **接口**：`POST /api/device`（新增）、`PUT /api/device`（编辑）
- **校验**：
  - 设备名称、型号、SN 不能为空；
  - SN 全局唯一（重复返回 `code=2001`）。

#### 2.3.4 生成设备二维码

- **规则**：每个设备的二维码内容就是一个字符串，例如：`MED-DEVICE-101`（前缀 + 设备 ID）。
- **后端接口**：`GET /api/device/{id}/qrcode` 返回一张 PNG 图片（用 ZXing 或 Google Zxing 库生成）。
- **App 扫码逻辑**：
  - 扫到内容后，解析出设备 ID；
  - 调 `GET /api/device/{id}` 拿详情；
  - 进入设备详情页。

### 2.4 扫码报修模块

#### 2.4.1 提交报修单

- **入口**：App 首页大按钮"扫码报修"，或设备详情页底部"报修"按钮。
- **流程**：
  1. 扫码（或从详情页进入）→ 显示设备名称、型号、SN；
  2. 用户填写：故障描述（多行文本，必填，≤500 字）、故障图片（最多 3 张，可选）；
  3. 提交；
  4. 后端生成工单编号，状态初始为"待受理"。

- **接口**：`POST /api/repair-order`（multipart/form-data）
- **参数**：
  | 字段 | 类型 | 必填 | 说明 |
  |---|---|---|---|
  | deviceId | Long | 是 | 设备 ID |
  | description | String | 是 | 故障描述 |
  | images | File[] | 否 | 最多 3 张图片 |

- **响应**：返回工单编号 `orderNo`，例如 `BX202611100001`。

- **工单编号规则**：`BX + yyyyMMdd + 4 位当日序号`，例如 `BX202611100001`。

#### 2.4.2 我的工单

- **入口**：底部 Tab "我的工单"（nurse 角色）
- **接口**：`GET /api/repair-order/my?status=0&pageNum=1&pageSize=10`
  - `status=0` 表示全部；
  - 可选值：0 全部、1 待受理、2 维修中、3 已完成、4 已评价。
- **App 展示**：工单卡片显示工单编号、设备名、状态、提交时间。

---

### 2.5 工单管理模块

#### 2.5.1 工单状态机

```
[待受理] --engineer 接单--> [维修中]
[维修中] --engineer 完工--> [待评价]
[待评价] --nurse 评价--> [已完成]
[任意状态] --admin 关闭--> [已关闭]
```

状态枚举：
| 值 | 含义 | 可执行操作 |
|---|---|---|
| 1 | 待受理 | engineer 接单、admin 转派/关闭 |
| 2 | 维修中 | engineer 完工、admin 转派/关闭 |
| 3 | 待评价 | nurse 评价（1-5 星 + 文字）、admin 关闭 |
| 4 | 已完成 | 无 |
| 5 | 已关闭 | 无 |

#### 2.5.2 工单列表（engineer/admin）

- **接口**：`GET /api/repair-order/page?status=1&pageNum=1&pageSize=10`
- **engineer 首页默认显示"待受理 + 维修中"的工单**。

#### 2.5.3 工单详情

- **接口**：`GET /api/repair-order/{id}`
- **返回**：工单信息 + 设备信息 + 报修人信息 + 处理人信息 + 图片列表 + 操作日志（谁在什么时候做了什么）。

#### 2.5.4 接单

- **角色**：engineer
- **接口**：`PUT /api/repair-order/{id}/accept`
- **后端逻辑**：
  - 校验当前状态必须是"待受理"；
  - 将工单状态改为"维修中"；
  - 记录 `assignee_id` = 当前 engineer ID；
  - 写入操作日志。

#### 2.5.5 完工

- **角色**：engineer
- **接口**：`PUT /api/repair-order/{id}/finish`
- **参数**：维修说明 `repairRemark`（必填）、维修图片（可选）
- **后端逻辑**：
  - 校验状态必须是"维修中"；
  - 状态改为"待评价"；
  - 设备状态同步改回"正常使用"（除非工程师标记为"报废"）。

#### 2.5.6 评价

- **角色**：nurse（只能评价自己提交的工单）
- **接口**：`PUT /api/repair-order/{id}/rate`
- **参数**：评分 `rating`（1-5 整数）、评价文字 `comment`（可选）
- **后端逻辑**：状态改为"已完成"。

#### 2.5.7 转派/关闭（admin）

- **转派**：`PUT /api/repair-order/{id}/assign`，参数 `engineerId`
- **关闭**：`PUT /api/repair-order/{id}/close`，参数 `closeReason`

---

### 2.6 巡检任务模块（P1）

#### 2.6.1 巡检任务生成

- **规则**：
  - 每个设备有 `next_inspect_date`（下次巡检日期）；
  - 每天凌晨 0:05，后端定时任务扫描所有设备：
    - 如果 `next_inspect_date <= 今天` 且状态为"正常使用"；
    - 自动生成一条巡检任务，分配给负责该科室的工程师。

- **后端实现**：Spring `@Scheduled(cron = "0 5 0 * * ?")`
- **任务表**：见 3.4 节。

#### 2.6.2 巡检打卡

- **角色**：engineer
- **接口**：
  - 列表：`GET /api/inspect-task/my?status=0`
  - 打卡：`PUT /api/inspect-task/{id}/submit`
- **打卡参数**：
  - `result`（1 正常 / 2 异常）；
  - `remark`（备注）；
  - `images`（异常时拍照，可选）。
- **异常情况**：engineer 标记异常后，自动生成一条报修工单（关联该设备）。

---

### 2.7 通知公告模块（P1）

- **通知类型**：
  | 类型 | 触发时机 | 接收人 |
  |---|---|---|
  | 工单已受理 | engineer 接单后 | 报修护士 |
  | 工单已完工 | engineer 完工后 | 报修护士 |
  | 检定到期提醒 | 每天定时扫描，提前 30 天 | admin + engineer |
  | 巡检任务派发 | 定时任务生成巡检任务 | 对应 engineer |

- **接口**：
  - 列表：`GET /api/notification/my?pageNum=1&pageSize=10`
  - 标记已读：`PUT /api/notification/{id}/read`
  - 未读数：`GET /api/notification/unread-count`

---

### 2.8 统计报表模块（P2）

- **入口**：admin 首页
- **接口**：`GET /api/stats/overview?month=2026-11`
- **返回**：
  ```json
  {
    "deviceTotal": 320,
    "deviceNormalRate": 0.96,
    "repairThisMonth": 18,
    "repairFinished": 15,
    "repairPending": 3,
    "avgFinishHours": 24.5
  }
  ```
- **App 展示**：用简单的数字卡片 + 一个 ECharts（Android 端用 MPAndroidChart）饼图。

---

### 2.9 导出 Excel（P2）

- **接口**：`GET /api/stats/export?month=2026-11`
- **返回**：一个 `.xlsx` 文件流，包含当月所有报修工单明细。
- **技术**：EasyExcel。

## 三、数据库设计

### 3.1 ER 关系概览

```
sys_user (1) ──── (N) repair_order (reporter_id)
sys_user (1) ──── (N) repair_order (assignee_id)
medical_device (1) ──── (N) repair_order
medical_device (1) ──── (N) inspect_task
sys_user (1) ──── (N) inspect_task (inspector_id)
sys_user (1) ──── (N) notification
```

### 3.2 建表 SQL

```sql
-- ============== 1. 用户表 ==============
CREATE TABLE sys_user (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
    username      VARCHAR(50)  NOT NULL UNIQUE COMMENT '登录名',
    password      VARCHAR(100) NOT NULL COMMENT '密码（BCrypt加密）',
    real_name     VARCHAR(50)  NOT NULL COMMENT '真实姓名',
    role          VARCHAR(20)  NOT NULL COMMENT '角色：admin/engineer/nurse',
    dept          VARCHAR(50)  COMMENT '所属科室',
    phone         VARCHAR(20)  COMMENT '手机号',
    status        TINYINT      NOT NULL DEFAULT 1 COMMENT '1启用 0禁用',
    create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) COMMENT '系统用户表';

-- ============== 2. 医疗设备表 ==============
CREATE TABLE medical_device (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    device_name         VARCHAR(100) NOT NULL COMMENT '设备名称',
    model               VARCHAR(100) COMMENT '型号',
    sn_code             VARCHAR(100) NOT NULL UNIQUE COMMENT '设备序列号',
    department          VARCHAR(50)  COMMENT '使用科室',
    location            VARCHAR(100) COMMENT '具体位置（如：内科3病房）',
    supplier            VARCHAR(100) COMMENT '供应商',
    purchase_date       DATE         COMMENT '采购日期',
    status              TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 2维修中 3停用 4检定中',
    last_inspect_date   DATE         COMMENT '上次巡检日期',
    next_inspect_date   DATE         COMMENT '下次巡检日期',
    verify_expire_date  DATE         COMMENT '计量检定到期日期',
    create_time         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) COMMENT '医疗设备表';

-- ============== 3. 报修工单表 ==============
CREATE TABLE repair_order (
    id             BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no       VARCHAR(30)  NOT NULL UNIQUE COMMENT '工单编号 BX+yyyyMMdd+序号',
    device_id      BIGINT       NOT NULL COMMENT '设备ID',
    reporter_id    BIGINT       NOT NULL COMMENT '报修人ID',
    assignee_id    BIGINT       COMMENT '处理人ID',
    description    VARCHAR(500) NOT NULL COMMENT '故障描述',
    images         VARCHAR(1000) COMMENT '现场图片URL，逗号分隔',
    status         TINYINT      NOT NULL DEFAULT 1 COMMENT '1待受理 2维修中 3待评价 4已完成 5已关闭',
    repair_remark  VARCHAR(500) COMMENT '维修说明',
    rating         TINYINT      COMMENT '评分1-5',
    comment        VARCHAR(500) COMMENT '评价文字',
    finish_time    DATETIME     COMMENT '完工时间',
    close_reason   VARCHAR(200) COMMENT '关闭原因',
    create_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_device (device_id),
    INDEX idx_reporter (reporter_id),
    INDEX idx_assignee (assignee_id),
    INDEX idx_status (status)
) COMMENT '报修工单表';

-- ============== 4. 巡检任务表 ==============
CREATE TABLE inspect_task (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    device_id     BIGINT      NOT NULL,
    task_date     DATE        NOT NULL COMMENT '巡检日期',
    inspector_id  BIGINT      COMMENT '巡检人ID',
    status        TINYINT     NOT NULL DEFAULT 1 COMMENT '1待巡检 2已完成 3异常转报修',
    result        TINYINT     COMMENT '1正常 2异常',
    remark        VARCHAR(500),
    images        VARCHAR(1000),
    create_time   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_device (device_id),
    INDEX idx_inspector (inspector_id),
    INDEX idx_date (task_date)
) COMMENT '巡检任务表';

-- ============== 5. 通知表 ==============
CREATE TABLE notification (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id       BIGINT      NOT NULL COMMENT '接收人',
    title         VARCHAR(100) NOT NULL,
    content       VARCHAR(500) NOT NULL,
    type          VARCHAR(30) NOT NULL COMMENT 'REPAIR_ACCEPTED/REPAIR_FINISHED/VERIFY_EXPIRE/INSPECT_ASSIGNED',
    is_read       TINYINT     NOT NULL DEFAULT 0,
    ref_id        BIGINT      COMMENT '关联业务ID（如工单ID）',
    create_time   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user (user_id, is_read)
) COMMENT '通知表';

-- ============== 6. 工单操作日志表 ==============
CREATE TABLE repair_order_log (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id      BIGINT      NOT NULL,
    operator_id   BIGINT      NOT NULL,
    action        VARCHAR(30) NOT NULL COMMENT 'SUBMIT/ACCEPT/FINISH/RATE/CLOSE/ASSIGN',
    detail        VARCHAR(500),
    create_time   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_order (order_id)
) COMMENT '工单操作日志';
```

### 4.4 JWT 鉴权流程

1. 登录成功后，后端生成 JWT（包含 userId、role、username），有效期 2 小时；
2. App 后续请求在 Header 带 `Authorization: Bearer {token}`；
3. `JwtAuthenticationFilter` 拦截请求：
   - 解析 token → 拿到 userId 和 role；
   - 存入 `SecurityContextHolder`；
4. 接口上用 `@PreAuthorize("hasRole('admin')")` 控制权限。

### 4.5 Redis 使用场景

| `device:detail:{id}` | 设备详情缓存 | 30 分钟 |
| `order:no:seq:{yyyyMMdd}` | 工单编号当日序号 | 当天 |
| `notification:unread:{userId}` | 未读通知数 | 5 分钟 |

**缓存穿透处理**：查询不到设备时，往 Redis 写一个空值标记（10 分钟过期）。
**缓存击穿处理**：查设备详情时，用 Redis 分布式锁（SETNX）重建缓存。

    override fun intercept(chain: Interceptor.Chain): Response {
        val token = DataStoreUtil.getToken()
